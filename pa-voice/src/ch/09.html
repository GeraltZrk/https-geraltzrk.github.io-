怎么让 AI 也照着这套规矩写

把规范拆给三方：代码管事实和发不发，规则检查管字数和红线，模型只管措辞。三样东西打包成一个 Skill，人读的和模型加载的是同一批文件。

一段提示词为什么不够

把这份手册整段贴进提示词，模型会写得更像样，但有三类事它做不稳。第一类是事实：让模型把几条来源揉成一句话，Apple 的通知摘要就出过把新闻通知改写成假标题的事故。第二类是字数和禁用说法：模型数不准字，结构化输出也不提供长度约束。第三类是「发不发」：2024 年的一项公开评测里，GPT-4o 等模型主动开口的误报率在一半上下。

已经在线上跑的个人 agent 给出的做法很一致：负责执行的部分只转述事实，负责说话的部分只管措辞，不值得说就等（据一份泄露的提示词，厂商未确认）；后台任务和用户之间加一道闸，只放行能行动的信息，闸出错时默认不通知；没有新内容就只回一个约定的静默标记。

所以这套规范落成三层，每层交给最擅长它的一方。

① 代码事件进来，先过闸有没有新变化、是否在授权内、频率上限、安静时段。多数事件在这一步变成「不发」或「进小结」。
② 代码写入事实槽位金额、时间、比较基准、来源、查询时刻。模型只读，不能改，也不能自己算出新的数。
③ 模型 + Skill选类型、定档位、写14 种消息类型选一种；七个语气参数按情境定档；先写只报事实的一版，再有条件地加一笔。
④ 代码体检22 项规则检查，外加逐个核对文案里的数字都在事实槽位里。有「必改」就退回重写，最多两轮。
⑤ 代码发出，或降级两轮都没过，就发按模板拼出来的事实版。付款和对外发送永远等用户点。

这张流程图是本手册的设计，不是某个产品的实现。其中「模型只管措辞」「闸出错时默认不发」「没有新内容就静默」三点有线上系统的先例，见上面的角标。

规则检查只抓得住一部分它查得出字数、绝对化用语、相对时间、促销腔和缩写。它查不出「会议已预调」其实只是备好了草稿，也查不出「高于均价 ¥80」里的均价是哪段时间的。前一类问题交给代码，每条都查；后一类要靠评审量表里的「事实保真」和「不操纵」两个维度，模型先筛，人来定。

Skill 包里有什么 pa-voice-zh · 15 个文件

Skill 是一种开放的打包格式：一个文件夹，里面有一份带元信息的 SKILL.md，加上按需读取的参考文件和脚本。模型平时只看见一句描述，判断用得上才读正文，正文再指向更细的文件。这样规范可以分层写，又不会每次都占满上下文。

这个包按官方写法组织：正文只写模型原本不知道的东西；每条规则带一句原因和一组正反例；能用代码判定的都放进脚本。

文件管什么谁在用
SKILL.md五步流程、类型表、写法、输出格式、任何档位都不做的事模型，每次
references/发送策略、14 种类型的模板、语气档位、幽默阶梯、词表、容器预算、全部规则模型，按需
assets/消息和用户档案的结构定义；场景话术库（示例）代码与模型
scripts/体检脚本，和本页的体检器是同一份代码代码，每次
evals/46 条回归用例、评审量表、评测用的提示词和配对办法改规范、换模型时
 

      

    

    

      
用法一：直接装成 Skill把 pa-voice-zh/ 文件夹放进支持 Agent Skills 的工具（例如项目的 .claude/skills/ 目录）。模型遇到写主动消息的任务时会自己加载。

      
用法二：接进自己的生成链路SKILL.md 作为系统提示词，按消息类型从示例库里取 3–5 条放进上下文，输出按 message.schema.json 约束，生成后跑 lint.mjs。

      
用法三：只用体检不换模型、不改提示词，只把 node scripts/lint.mjs 接在现有文案的发布流程后面，先把字数、称呼混用、绝对化用语拦下来。

评测按「同一批情境，带 Skill 和不带各写一遍，评审不知道哪个是哪个」的办法做。写的一方是同一个模型，区别只在读没读过这套 Skill。情境覆盖机会、扣款提醒、求拍板、按授权已办、需要接管、延误、更正、放弃、里程碑、长辈模式、监控故障、定时提醒、缺比较基准和周报，其中几条的正确答案是「不发」。用例里的金额、日期和商品，都不和 Skill 里的示例重复。每改一次规范就补一批新用例；第三轮起，新用例由没看过规范改动的模型出题，另一个模型核对日期和算术。

        
分三层判。发不发在不在预期之内、该出现的数字有没有出现、禁用说法有没有出现，由代码判定。字数和格式由体检脚本判定。哪一条能让这位用户更快做出正确的决定，由三位评审盲评，它们分别扮演产品经理、中文文案编辑和合规审查。第三轮起同一批输出看两遍：一遍给评审完整的文字，一遍只给这个位置上显示得出来的部分。

不能说明什么写的和评的是同一个模型，评审是模型扮演的，不是用户，而且评审偏爱更长的回答这类偏差有据可查；情境是模型出的；每个情境每边只写 2 遍，单条的胜负晃得厉害，只能看合计。它不能替代真人评审和线上数据。写作风格这类主观的东西，官方工具也建议以人工定性评审为主。

用户的偏好不放进 Skill称呼、要不要玩笑、安静时段，属于每个用户的档案，放在记忆层。只记用户明说的和显式设置的，区分「他说的」和「我们推断的」，推断不能覆盖明说。

        
长对话里人设会漂有研究在八轮对话之内就观察到语气明显偏离设定。主动消息每条都是单独生成的，这反而是优势：每次都从同一份 Skill 和同一份档案出发。

        
词表会过期，结构不会模型的口癖每一代都在变，结构上的毛病更持久。词表当检查线索用，不当黑名单用；每换一代模型，重跑用例，重看一遍哪些词还在冒出来。

        
定时任务不会自己推断语言有的 agent 框架明确写了：后台任务不会从渠道或历史里推断回复语言，语言规则必须写进任务提示词。中文规范要显式加载。
